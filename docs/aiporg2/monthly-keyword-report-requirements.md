# 월간 온라인 여론 키워드 보고서 상세 요구사항

작성일: 2026-10-16. 상태: 사용자 요구사항 및 구현 설계안. 코드 구현 완료 문서가 아니다.

## 1. 최종 목표와 기준 자료

매월 사용자가 지정하는 핵심 키워드 4~5개를 대상으로 온라인 자료를 수집하고, 근거가 연결된 통계와 서술을 작성한다. 사용자가 Streamlit에서 직접 수정·검수·승인한 뒤, 제공한 7월 보고서와 같은 구성과 시각적 완성도의 편집 가능한 HWPX를 생성한다. Word와 Markdown도 같은 승인본에서 출력한다.

최우선 기준은 사용자 제공 `2026년도 7월 충남 온라인여론 키워드조사 분석 보고서(이경환검토후편집예정).pdf` 12쪽이다. 텍스트 추출과 전체 페이지 렌더링을 함께 확인했다. 이전 3월 PDF는 보조 자료이며, 이전 문서의 단순 텍스트 보고서나 디자인 재현 제외 전제보다 이번 요구를 우선한다.

“키워드만 달라진다”는 뜻은 문서의 브랜드·장 구성·편집 규칙을 재사용한다는 것이다. 실제 제목, 사실, 기간, 수치, 순위, 표 행, 그림, 출처, 시사점은 해당 월의 수집 결과로 새로 만든다. 참고본의 사건·인물·수치·Lucy 사용 문구를 고정 내용으로 복사하지 않는다. 참고본 자체의 사실 검증은 이번 문서 분석에서 수행하지 않았다.

### 확정된 사용자 요구

- 월별 핵심 키워드 약 4~5개 입력.
- 네이버·다음·구글·인스타그램·X·각종 커뮤니티 등 여러 출처 수집.
- 7월 보고서의 목차, 서술, 표, 이미지 수준을 기준으로 제작.
- 표와 이미지는 수집 내용에 맞춰 매월 직접 생성.
- GPT 또는 Claude로 서술 초안 생성, 사용자가 수정·승인한 후 출력.
- HWPX가 주 산출물. Word·Markdown 출력도 유지.
- 별도 python-hwpx 저장소를 의존성으로 사용하고 필요한 공통 기능을 확장.

### 설계 제안과 미확정 사항

| 항목 | 제안 | 확정 전 처리 |
| --- | --- | --- |
| 고정 조사어 | 지역·기관·인물의 기본 조사어 + 월별 이슈 키워드 | 월별 키워드만 조사하면 보고서 범위도 해당 키워드로 한정. 지역 전체 여론으로 표현하지 않음 |
| 댓글 | 본문과 접근 가능한 댓글을 분리 수집·집계 | 댓글 포함 여부는 사용자 미응답. 본문 통계와 자동 합산하지 않음 |
| 커뮤니티 | 사용자 지정 사이트·게시판 목록 | “각종 커뮤니티 전체”를 완료 기준으로 쓰지 않음 |
| 유튜브·블로그 | 7월 기준본의 6개 채널 구성에 포함 | 실제 수집 가능 범위 검증 후 활성화 |
| 외부 여론조사 | 검증된 원자료가 있을 때만 별도 영역에 수록 | 자료 없으면 미확보 표시 또는 검수 후 해당 블록 제외 |
| 첫 달 비교 | 전월도 동일 조건으로 수집하거나 기존 검증 자료 연결 | 없으면 전월 대비 산출 불가 표시 |

위 미확정 항목은 문서 작성의 장애물이 아니다. 다만 실제 수집 범위와 신규 저장 계약은 구현 전에 결정해야 한다.

## 2. 사용자가 수행하는 전체 업무

1. 조사 월, 대상 지역·기관, 핵심 키워드 4~5개와 동의어·제외어를 입력한다.
2. 수집 채널·커뮤니티 목록·댓글 포함·비교기간을 확인하고 수집을 실행한다.
3. 채널별 성공·부분 수집·미지원 상태와 수집 건수를 확인한다.
4. 관련 없는 자료와 중복 판정을 검토하고 집계 대상을 확정한다.
5. 이슈별 사실, 감성 분류, 관련 키워드, 통계와 표·그림 초안을 확인한다.
6. GPT/Claude로 장별 서술 초안을 생성한다.
7. 원문과 숫자를 보면서 문장을 수정하고 필요한 부분만 재생성한다.
8. 표·그림과 본문이 연결된 미리보기를 검수하고 버전 단위로 승인한다.
9. 승인된 같은 버전으로 HWPX·DOCX·Markdown을 출력한다.
10. 다음 달에는 프로젝트 설정을 복사하고 조사 월·핵심 키워드를 변경한다. 이전 달 결과는 보존한다.

## 3. 입력과 수집 범위

### 3.1 월간 조사 설정

필요 정보는 조사 월, Asia/Seoul 기준 시작·종료 시각, 대상 지역·기관·인물, 보고서 제목, 핵심 키워드 그룹, 동의어, 제외어, 수집 경로, 원문 채널, 커뮤니티 목록, 댓글 정책, 비교기간, 보고서 템플릿 버전이다. 이는 필요한 정보 목록이며 새 Pydantic schema를 바로 추가하라는 지시가 아니다.

월간 기간은 해당 월 1일 00:00 이상, 다음 달 1일 00:00 미만이다. 수집 시각이 아니라 게시 시각으로 대상 기간을 판정한다. 게시 시각을 확인할 수 없는 자료는 별도 보류하고 월별 통계에 조용히 포함하지 않는다.

핵심 키워드 하나는 단일 문자열이 아니라 하나의 조사 주제다. 예를 들어 `집중호우` 그룹에는 관련 지역명, `침수`, `수해`, `산사태` 등을 검토하여 넣을 수 있다. 시스템의 자동 추천은 사용자가 확인한 후 검색 조건에 반영한다. 이 예시는 실제 이번 달 조사어가 아니다.

동명이인·타지역·다른 사업과의 혼동을 막기 위해 지역 및 기관 맥락과 제외 조건을 보관한다. 하나의 게시물이 두 키워드 그룹에 해당할 수 있으므로 키워드별 합계와 전체 고유 게시물 수는 별개다.

### 3.2 검색 경로와 분석 채널 분리

| 구분 | 예 | 처리 |
| --- | --- | --- |
| 발견 경로 | 네이버, 다음, 구글 | 어떤 검색에서 발견했는지 기록 |
| 원문 채널 | 뉴스·언론, X, 인스타그램, 유튜브, 커뮤니티, 블로그 | 실제 원문 출처로 통계 분류 |
| 원문 사이트 | 언론사 도메인, 특정 게시판 | 출처와 수집 범위 설명에 사용 |
| 문서 유형 | 기사, 게시물, 영상 설명, 댓글, 답글 | 서로 다른 집계 단위를 구분 |

네이버와 구글에서 같은 기사를 발견해도 기사 한 건이다. 검색 결과 건수와 실제 확보한 원문 건수는 다르다. 검색엔진이 표시하는 추정 전체 건수를 월간 언급량으로 사용하지 않는다.

### 3.3 수집 어댑터별 요구

| 경로/채널 | 확보 대상 | 구현 시 확인할 사항 |
| --- | --- | --- |
| 네이버 | 뉴스·블로그·접근 가능한 기타 원문 | 검색 유형별 기간 제한, 페이지 순회, 본문 확보, API 범위 |
| 다음 | 뉴스 및 대상 원문 | 검색 결과의 실제 도메인, 날짜 필터, 페이지 순회 |
| 구글 | 지정 기간·키워드의 웹 문서 발견 | 사용 가능한 검색 인터페이스, 검색 날짜와 원문 날짜 차이 |
| X | 게시물·답글·인용/재게시 관계 | 인증·비용·과거 검색 범위·호출 한도·원문 보존 범위 |
| 인스타그램 | 접근 가능한 게시물·캡션·댓글 | 계정·권한별 가능 범위, 해시태그·기간 검색 제약 |
| 유튜브 | 영상 제목·설명·접근 가능한 댓글 | 영상/댓글 게시일 구분, 페이지 순회, 자막 확보 여부 |
| 커뮤니티 | 확정한 사이트·게시판의 글·댓글 | 사이트별 검색/본문/날짜 구조, 접근 실패, 삭제글 처리 |
| 블로그 | 제목·본문·게시일·원문 주소 | 검색 경로 중복, 광고·관련 없는 글 판정 |

각 어댑터 착수 시 공식 문서와 실제 접근 권한으로 가능 범위를 검증한다. 현재 문서는 모든 플랫폼의 과거 자료를 완전 수집할 수 있다고 보장하지 않는다. 월말 일괄 검색과 월중 누적 수집의 확보량 차이를 확인하고, 과거 검색 제한이 있는 출처는 주기 수집을 설계한다. 실제 스케줄 등록은 별도 구현 작업이다.

### 3.4 수집 기록과 실패 처리

- 원문 URL·플랫폼 ID, 검색 경로, 채널, 제목·본문, 게시 시각·수집 시각, 키워드 매칭, 원문 근거 위치를 저장한다.
- 댓글은 부모 글·답글 관계를 보존한다. 재게시와 실질적인 새 의견이 있는 인용 게시물을 구별한다.
- 조회·좋아요·공유 수는 수집 당시 값과 시각을 함께 기록한다. 제공되지 않은 수치는 0이 아닌 미확보 값이다.
- 채널 상태는 성공, 일부 성공, 인증 필요, 한도 초과, 미지원, 실패 등을 구분한다. 이는 필요한 화면 상태이며 기존 workflow enum의 즉시 변경을 뜻하지 않는다.
- 실행별 검색식·페이지 범위·시도·오류·재시도 위치를 보존한다. 재시도해도 동일 원문을 중복 저장하지 않는다.
- 검색 결과만 있고 본문이 없는 자료와 본문까지 확보한 자료를 구분한다. 제한된 스니펫에서 전체 글의 입장을 단정하지 않는다.
- 미수집 채널을 0건으로 표시하지 않는다. 보고서에 실제 확보 채널과 조사 범위를 명시한다.

## 4. 정제·분석·수치 산출 규칙

### 4.1 정제와 근거

URL 정규화 → 동일 플랫폼 ID/URL 중복 → 본문 중복 후보 → 관련성 판정 → 분석 대상 확정 순서로 처리한다. 원문은 보존하고 정제본을 분리한다. 동일 보도자료 전재는 고유 내용 수와 실제 게시 건수 중 어떤 지표인지 구분하고, 적용한 중복 정책을 보고서 방법론에 쓴다.

사실에는 근거 문서, 인용 구간, 게시일, 사건 발생일(확인 가능할 때), 출처, 검증 상태가 필요하다. 기사에 나온 사업비나 피해 규모는 수집 문서 수와 다른 종류의 숫자이며 원문 근거를 연결한다. LLM이 기사 서술을 외부에서 독립 검증한 사실처럼 표현하지 않도록 출처와 확실성을 유지한다.

### 4.2 지표 정의

| 지표 | 산식·기준 | 예외 |
| --- | --- | --- |
| 전체 언급량 | 승인된 범위의 고유 분석 문서 수 | 댓글 포함 지표는 별도 이름·분모 |
| 채널 언급량 | 해당 원문 채널의 분석 문서 수 | 발견 검색엔진별 건수와 구분 |
| 채널 비중 | 채널 건수 / 동일 범위 전체 건수 × 100 | 전체 0이면 산출 불가 |
| 이슈 언급량 | 해당 이슈에 매핑된 고유 문서 수 | 이슈 간 중복 가능, 합산 주의 |
| 전월 증감 건수 | 이번 달 건수 - 전월 건수 | 수집 범위·방법이 다르면 비교 제한 |
| 전월 증감률 | (이번 달 - 전월) / 전월 × 100 | 전월 0은 신규/비교 불가, 무한대 금지 |
| 긍정 비율(중립 포함) | 긍정 / (긍정+부정+중립) × 100 | 미분류는 제외하되 미분류율 공개 |
| 긍정 비율(중립 제외) | 긍정 / (긍정+부정) × 100 | 기준본 p10 방식. 분모와 표본 수 표시 |
| 전월 감성 차이 | 동일 분모 기준 비율 차이 | %가 아닌 %p 사용 |
| 연관 키워드 순위 | 정규화된 키워드의 문서 빈도 내림차순 | 동일 글의 반복 횟수로 부풀리지 않음 |
| 참여 지표 | 관측 시각이 있는 좋아요·댓글·공유 등 | 플랫폼 간 단위가 다르면 단순 합산 금지 |

비율 표시 자릿수와 반올림 정책을 고정한다. 반올림 합계가 100%와 다를 때 각주로 설명하며 숫자를 임의 조정하지 않는다. 요약·본문·표·그림은 같은 AnalyticsSnapshot과 같은 지표 경로를 참조한다.

### 4.3 감성·입장·이유 분석

긍정·부정·중립·미분류를 구분하고 분석 대상(정책/인물/재난 대응 등)을 지정한다. 재난 피해를 슬퍼하는 표현과 행정 대응을 비판하는 표현은 다르다. 정책 찬반과 일반 감성도 별도 개념으로 다룬다. 비꼼·혼합 의견·근거 부족 자료는 검수 대상으로 표시한다.

분류 방법·모델/사전 버전·판정 근거·수동 수정 이력을 남긴다. 현재 metadata 라벨 집계만으로 미분류 문서의 감성을 분석했다고 주장하지 않는다. 분류기에 LLM을 도입할지는 별도 계약 결정 대상이며 Collector에서 호출하지 않는다.

긍정·부정 이유는 각 이유를 뒷받침하는 문서 묶음과 함께 제시한다. 최대 5개를 편집 목표로 삼되 근거가 2개 유형이면 2개만 작성한다. 숫자나 이유 개수를 채우기 위한 생성은 금지한다.

이용자의 연령·성별·직업·거주지는 글이나 출처에 신뢰 가능한 근거가 없으면 추정하지 않는다. 온라인 수집 감성 비율을 도민 지지율·직무평가 조사로 표시하지 않는다.

### 4.4 TOP20과 평가 표시

한국어 형태·복합어·동의어·불용어 정규화 규칙을 먼저 정한다. 핵심 입력어와 새롭게 발견된 연관어를 구별하고 순위 포함 정책을 명시한다. 기본 순위는 문서 빈도, 동률은 고정된 보조 정렬 기준으로 재현 가능하게 만든다. 검증되지 않은 “확산 강도” 가중치를 만들지 않는다.

참고본의 별점은 산식이 제시되어 있지 않다. 초기 구현은 실제 언급 건수·비율 또는 근거가 연결된 감성 라벨을 사용한다. 별점을 유지하려면 점수 대상·분모·변환 구간을 먼저 확정하고 보고서에 표기한다. 스타일을 재현하기 위해 임의의 별점을 채우지 않는다.

### 5.1 표지·목차·공통 스타일

A4 세로, 넓은 흰 여백, 남색 장 제목과 구분선, 파란 표 머리행, 연한 청색/회색 교대 행, 상단 월간 리포트명, 하단 가운데 `- n -` 페이지 번호를 기준으로 한다. 인포그래픽은 연한 청색 배경과 흰색 또는 아이보리 둥근 카드 구성을 재사용한다.

정확한 글꼴·크기·여백은 원본 HWPX 확보 후 추출하는 것이 우선이다. PDF만으로 내부 문단 스타일·페이지 설정을 완전히 복원했다고 주장하지 않는다. 원본이 없으면 대표 페이지를 재현하여 한컴 렌더 결과로 시각 기준을 확정한다. 초기 조판 시안의 본문 크기 등은 제안값이지 PDF에서 검증된 측정값이 아니다.

표지 사진과 로고는 재사용 가능한 원본 자산을 등록한다. 참고본 전체 페이지를 이미지로 붙여 편집 가능한 HWPX인 것처럼 납품하지 않는다. 참고본의 잘린 로고, 불명확한 아이콘 글리프, 장 제목만 전 페이지에 남는 편집 문제는 재현 대상에서 제외한다.

### 5.2 요약 페이지

상단 4개 카드: 기간 / 실제 확보 채널 수 / 월별 핵심 키워드 / 선택한 범위의 긍정 비율 및 전월 차이. 키워드가 길면 줄바꿈·요약 표기하고 전체 목록은 개요에 둔다.

이슈 카드: 사용자 키워드 그룹에 대응하는 이슈명, 아이콘, 핵심 사실 1문장, 의미 1문장. 4개는 가로 4열을 기준으로 하되 5개는 3+2 배열 등 읽기 가능한 레이아웃을 사용한다. 이슈명은 고정 주제명을 강요하지 않고 해당 월 결과에 맞춘다.

하단: 채널 비중 도넛 + 감성 요약 2열, 이슈별 핵심 시사점 번호표. 전체 본문이 검수된 후 요약을 갱신하여 본문에 없는 새로운 주장이 들어가지 않게 한다.

### 5.3 이슈별 공통 서술 구조

각 이슈는 제목 → 발생 배경과 월간 경과 → 확인된 주요 사실 → 온라인 반응과 쟁점 → 표/그림 → 해석과 제한 → 출처 순서다. 본문은 보고서 문체로 쓰며 근거에 따라 “확인됨”, “보도됨”, “수집 자료에서 나타남”, “해석할 수 있음”을 구분한다.

| 이슈 유형 | 적합한 표 | 적합한 그림 |
| --- | --- | --- |
| 정책·사업 | 세부 사업 / 진행 상황 / 반응 또는 건수 | 진행 단계 카드, 근거 있는 지표 막대 |
| 재난·민원 | 발생 사안 / 확인 내용 / 반응·쟁점 | 사건 시간순 카드, 긍·부정 반응표 |
| 산업·일자리 | 세부 주제 / 발표·추진 내용 / 언급량 | 주요 내용 카드와 언급량 비교 |
| 갈등·공론화 | 쟁점 / 찬성 논거 / 반대 논거 / 확인 사항 | 입장별 비교표, 절차 타임라인 |
| 기타 신규 주제 | 하위 주제 / 사실 / 온라인 반응 | 공통 3열 카드 또는 연관어 비교 |

이는 7월의 취임·재난·AX·통합 주제를 고정하는 구조가 아니다. 다른 달 키워드에도 같은 편집 수준을 적용할 수 있는 공통 블록이다. 근거 없는 예산·인원·피해·지지율·인용문은 표에도 들어갈 수 없다.

### 5.4 외부 여론조사

참고본 p5의 직무수행 평가 그래프와 p10의 온라인 감성은 서로 다른 데이터다. 외부 조사 블록은 조사기관, 의뢰기관(확인 가능 시), 조사일, 대상 지역·모집단, 표본 크기, 조사 방법, 질문/지표 정의, 원자료 링크를 검수한 경우만 생성한다. 전국 평가와 지역 평가를 동일한 온라인 지표처럼 비교하지 않는다.

검증된 외부 조사가 없으면 해당 블록을 생략하거나 “검증된 외부 조사 자료 미확보”로 처리한다. 사용자 확인을 거쳐 온라인 자료 기반 표로 대체할 수 있으나 표 제목과 지표 의미도 변경해야 한다.

### 5.5 시사점과 출처

시사점 표는 관측된 문제 → 근거 → 해석 → 실무적으로 확인/개선할 사항 순서로 작성한다. 재난 안내, 민원 처리, 정책 설명의 명확성, 절차 공개 등 근거에 맞는 행정적 제언을 제시한다. 단순 동시 발생만으로 특정 행동이 감성 변화를 유발했다고 단정하지 않는다.

채널 표는 채널 / 관측된 현황 / 제안으로 구성한다. 채널별 이용자 특성·선호·조회수 호조를 실제 자료 없이 상식적으로 채우지 않는다. 조사하지 않은 채널의 진단은 작성하지 않는다.

출처는 매체·제목·게시일·URL을 포함하고 본문·표·그림의 근거 ID와 연결한다. 지면에는 주요 출처, 별도 근거 목록에는 전체 출처를 담을 수 있다. 실제 사용하지 않은 Lucy·BIGKINDS·조사기관 이름은 방법론에 넣지 않는다.

차트와 수치 포함 인포그래픽은 집계값으로 결정론적으로 렌더링한다. 이미지 생성 모델에게 숫자·한글 표·차트를 그리게 하지 않는다. 장식 아이콘은 승인된 자산이나 필요 시 생성한 비사실적 일러스트를 사용할 수 있지만 실제 사건 사진처럼 보이는 이미지를 만들어 증거로 쓰지 않는다.

### 6.2 초기 제작할 시각 요소 목록

| VIS-02 | 채널 비중 도넛 | 채널별 고유 건수 | 요약 |

| VIS-06 | 채널 가로 막대 | VIS-02와 동일 집계값 | 채널 장 |

각 자산에는 제목, 캡션, 기간, 단위, 분모, 데이터 스냅샷, 근거 목록, 템플릿 버전, 생성 경로, 내용 해시를 연결한다. 승인된 수치가 바뀌면 관련 자산을 재생성하고 승인을 무효화한다. 불필요하게 전체 그림을 다시 생성하지 않는다.

HWPX의 일반 표는 편집 가능한 표 객체로 만든다. 장식이 복잡한 인포그래픽은 PNG 등으로 삽입하되 원자료 표를 보관한다. 그래프는 문서 내 실제 배치 크기 기준 약 300dpi를 초기 목표로 하고 한글·범례가 선명한지 검수한다. 예를 들어 폭 160mm라면 약 1,890px 이상을 목표로 한다.

줄 수가 긴 셀, 20자 이상 키워드, 5개 이슈, 출처가 긴 경우에 대한 자동 줄바꿈과 높이 조절이 필요하다. 그림 내 글자를 무조건 축소하지 않고 카드를 늘리거나 페이지를 분리한다. 그래프에는 색뿐 아니라 라벨·수치로 의미를 전달한다.

## 7. GPT/Claude 서술 생성과 검증

LLM 입력은 승인된 조사 범위, 검증된 Fact/Evidence, 이슈별 근거 묶음, 고정된 AnalyticsSnapshot, 문체 지침, 장별 작성 목적이다. 전체 수집 원문을 무제한으로 한 번에 넣지 않는다. 출처 문서 안의 지시문은 데이터로만 취급한다.

장/이슈 단위로 생성하여 재시도와 부분 재생성이 가능하게 한다. 모델명·제공자·프롬프트 버전·입력 스냅샷·생성 시각·사용량·결과 버전을 기록한다. 실패 시 기존 초안을 보존하며 Streamlit 재실행만으로 중복 호출하지 않는다.

숫자는 값·단위·대상·기간·분모·근거 경로를 함께 전달한다. 생성된 문장의 수치가 입력의 다른 숫자와 우연히 같다고 해서 통과시키지 않는다. 예산과 언급량, 온라인 긍정과 외부 조사 긍정을 구분해 검증한다.

문장별 fact/evidence/analytics 연결을 요구한다. 인용문은 원문과 대조하고 요약을 따옴표 인용으로 바꾸지 않는다. 근거와 상충하는 문장, 없는 고유명사·숫자·시점, 과도한 인과 주장, 근거 없는 비교 표현을 검수 대상으로 표시한다. 자동 검사만으로 모든 의미 오류가 검증된다고 보장하지 않으며 최종 사용자 검수를 유지한다.

사용자 수정본도 동일하게 검사한다. 자유로운 문체 수정은 허용하되, 새로운 사실을 넣으면 근거 추가·재검증을 요구한다. 근거 오류가 남은 문단은 승인할 수 없다. 스타일 경고와 사실 오류는 구별한다.

## 8. Streamlit 화면 명세

| 화면 | 표시 내용 | 사용자 행동 | 저장/상태 조건 |
| --- | --- | --- | --- |
| 월별 프로젝트 | 월, 제목, 조사어, 이전 보고서 | 생성·복제·키워드 수정 | 변경 이력과 범위 버전 저장 |
| 수집 설정·실행 | 출처별 가능 범위, 댓글, 기간 | 실행·중지 요청·실패 재시도 | 작업 ID로 진행 추적, 화면 새로고침과 분리 |
| 수집 결과 검토 | 채널별 확보/제외/실패, 원문 목록 | 관련성·중복 검토 | 제외 이유와 검수자 변경 기록 |
| 통계·이슈 검토 | 건수, 감성 라벨, 순위, 비교기간 | 근거 확인·분류 수정 | 스냅샷 갱신 시 이후 초안 영향 표시 |
| 서술 편집 | 장별 초안, 오른쪽 원문·수치·출처 | 수정·저장·부분 재생성·버전 비교 | 초안 버전 영속 저장 |
| 시각 자료 편집·승인 | 표·그림·차트·인포그래픽별 미리보기, 원자료, 수정 전후 비교 | 내용·디자인 수정, 재생성, 개별 승인·승인 취소 | 근거 데이터에서 수치 수정, 자료별 승인 버전 영속 저장 |
| 보고서 미리보기 | 장별 본문·표·그림, 오류 목록 | 수정 요청·승인 | 승인 대상 버전/해시 고정 |
| 출력·이력 | 승인본, 파일, 검수 기록 | HWPX/DOCX/MD 다운로드 | 같은 승인본으로만 출력 |

Streamlit session state는 화면 상태만 담당한다. 초안·수정·승인·작업 진행은 repository를 통해 영속 저장한다. 새로고침이나 앱 재시작으로 승인 기록이 사라지면 안 된다.

UI상 논리 단계는 초안 → 검증 필요 → 검수 중 → 승인 → 출력이다. 이는 기존 workflow enum을 즉시 변경하는 지시가 아니다. 기존 상태 머신과 별도 문서 버전 상태를 어떻게 연결할지 계약 설계에서 결정한다.

승인에는 본문 버전, 집계 버전, 표/그림 버전, 템플릿 버전이 함께 묶인다. 하나라도 변경되면 이전 승인은 이전 산출물에만 유효하다. 새 문서는 재검수한다. 승인 후 다운로드 시 LLM을 다시 호출하지 않는다.

웹 화면 미리보기와 한컴의 최종 페이지 배치는 다를 수 있다. 실제 HWPX 렌더 기반 미리보기 가능 여부를 시제품에서 검증하고, 불가능한 초기 단계에는 화면에 이 차이를 명시하여 한컴 확인 절차를 둔다.

### 8.1 생성된 시각 자료의 개별 편집·승인 (사용자 추가 요구)

표·그림·차트·인포그래픽은 생성 이후에도 사용자가 UI에서 확인·수정·승인할 수 있어야 한다. 본문 승인만으로 시각 자료를 자동 승인하지 않는다. 최종 보고서 승인은 포함된 모든 시각 자료의 현재 버전이 승인된 경우에만 가능하다.

작업 흐름은 `자료 생성 → 개별 미리보기 → 내용/디자인 수정 → 다시 렌더링 → 수정 전후 비교 → 개별 승인 → 문서 배치 미리보기 → 최종 보고서 승인 → 출력`이다. 시각 자료 생성·수정·승인은 M4와 M5 사이를 반복하며, 최초 생성 이후 편집 화면으로 돌아올 수 있어야 한다.

편집 화면은 왼쪽에 장별 자료 목록과 상태, 중앙에 확대 가능한 미리보기, 오른쪽에 원자료·근거 및 편집 설정을 둔다. 각 항목에서 수정 저장, 다시 생성, 이전 버전 보기·복원, 승인, 승인 취소, 보고서 포함/제외를 제공한다. 필수 블록 제외는 보고서 구성 변경으로 표시하고 최종 검수를 요구한다.

| 유형 | UI에서 수정할 항목 | 수정 후 처리 |
| --- | --- | --- |
| 표 | 제목, 열 이름, 설명 셀, 행·열 순서, 표시 항목, 열 너비, 정렬, 글자 크기, 색상 | 편집 가능한 표와 미리보기 함께 갱신. 데이터 행 숨김은 표시 범위를 명시 |
| 차트 | 제목, 차트 종류, 계열 선택, 정렬, 색상, 범례, 축·단위·라벨, 표시 자릿수, 크기 | 동일 원자료로 재렌더링. 축 변경으로 오해가 생기지 않도록 범위와 단위 검사 |
| 인포그래픽 | 카드 제목·설명, 아이콘, 카드 순서, 배치, 강조색, 글자 크기 | 편집 가능한 구성 정보로 재생성하고 숫자·사실을 재검증 |
| 그림·이미지 | 자산 교체·업로드, 자르기, 비율 유지 크기 조절, 캡션, 대체 설명, 출처 | 새 이미지 미리보기·출처 확인 후 재승인. 실제 자료와 장식 구분 |

내용 편집과 디자인 편집을 구분한다. 문구·설명은 UI에서 직접 고칠 수 있으며 사실 변경은 근거와 대조한다. 수치 수정도 UI에서 가능하되 원자료/분류/집계 조건의 수정으로 연결하고 수정 이유·근거·이력을 보존한다. 그림 속 숫자만 바꿔 원자료와 불일치하게 만들지 않는다. 같은 숫자를 사용하는 본문·표·차트에는 변경 영향을 표시하고 함께 갱신·재검수한다.

이미지 파일만 저장하면 내부 문구·카드·차트 수정이 어렵다. 생성된 자료는 편집용 표 데이터, 차트 설정, 인포그래픽 구성 정보, 자산 참조와 렌더 결과를 함께 보존한다. 초기에 Streamlit의 폼·표 편집과 설정 패널로 수정하고 미리보기를 갱신하는 방식을 사용한다. 자유로운 캔버스 드래그 편집은 별도 확장 범위이며 최초 구현의 필수 조건은 아니다. 외부 업로드 이미지의 내부 요소 자동 분해는 보장하지 않고 교체·자르기·캡션 편집을 지원한다.

각 자료의 승인 기록은 검수자, 시각, 자료 버전, 원자료 버전, 편집 설정, 렌더 결과 해시와 연결한다. 구현할 저장 계약은 M0에서 기존 구조와 대조해 결정한다. 승인 후 색상·문구·데이터·이미지 중 하나라도 바꾸면 해당 자료는 재검수 상태가 되며 연결된 최종 보고서 승인도 무효화한다. 관련 없는 자료의 개별 승인은 유지한다.

재생성 중에는 승인을 비활성화하고 현재 설정과 일치하는 최신 미리보기가 준비된 뒤에만 승인할 수 있게 한다. 실패 시 이전 버전을 보존하되 오래된 미리보기를 새 버전으로 승인하지 못하게 한다. 이전 버전 복원도 새 작업 버전으로 기록하고 다시 확인·승인한다.

최종 출력은 승인한 렌더 결과와 표 데이터·설정 버전을 고정해 사용한다. 출력 단계에서 새 콘텐츠를 생성하거나 다른 이미지로 교체하지 않는다. HWPX 문서 안에서의 크기·페이지 배치는 최종 보고서 미리보기에서 별도로 확인한다. 다운로드 이후 외부 편집기의 변경은 앱 승인본과 별개이며 앱에서 재검수하려면 다시 가져오는 절차가 필요하다.

## 9. HWPX 중심 출력 구조

공통 승인 콘텐츠 → 문서 조립 → 형식별 writer 흐름을 사용한다. HWPX의 문단·표·그림 배치 규칙은 기준본을 따른다. DOCX는 같은 내용과 유사한 레이아웃, Markdown은 같은 본문·표·그림 링크를 제공하며 페이지 단위 동일 배치는 요구하지 않는다.

python-hwpx는 AIPORG와 별도 clone/fork한다. 로컬은 editable 개발, 배포와 CI는 고정 커밋/버전 사용을 권장한다. 현재 clone·설치·연결은 완료되지 않았다. 라이브러리 버전과 API는 연결 시 다시 확인한다.

AIPORG에는 월간 템플릿, 보고서 블록 조립, 차트 생성, 출처 목록, 승인본 export를 구현한다. 공통 HWPX 포맷 처리 오류나 필요한 기능은 별도 fork에서 수정한다. upstream 업데이트로 템플릿이 깨지지 않도록 고정 샘플로 확인한다.

시제품 우선 검증 항목은 표지, 편집 가능한 표, 긴 한글 셀, 이미지 비율, 머리말·꼬리말, 페이지 번호, 목차, 페이지 나누기, 장 제목과 본문 묶음이다. ZIP/XML 유효성만으로 완료 처리하지 않는다. 실제 한컴에서 열고 PDF로 출력하여 전체 페이지를 확인한다.

최종 산출물은 `report.hwpx`, `report.docx`, `report.md`, Markdown용 `assets/`, 근거/집계 내역, 생성 버전 정보다. 파일 이름은 프로젝트·월·승인 버전을 포함하도록 구현 단계에서 통일한다. 미승인 자료는 최종 산출물 경로에 섞지 않는다.

## 10. 현재 구현과의 차이

| 영역 | 확인된 기존 상태 | 추가해야 할 내용 |
| --- | --- | --- |
| 수집 | 2.0 네이버·다음 뉴스 경로 중심 | 다중 채널, 월간 페이지 순회·기간 검증, 실제 접근 권한·완전성 확인 |
| 네이버 | 현재 확인한 검색 요청은 첫 페이지 중심 | 전체 필요 페이지 순회와 종료/한도 처리 검증 |
| 분석 | 기존 라벨 기반 감성 집계, 단순 키워드 집계 | 신규 자료 분류, 의미 있는 한국어 연관어, 대상별 감성 검수 |
| 서술 | 결정론적 템플릿 일부 | GPT/Claude adapter, 문장 근거, 수정본·승인본 저장 |
| UI | 이번 요구의 검수 UI 미구현 | Streamlit 검수·승인 전체 흐름 |
| 문서 | 1.0 DOCX와 차트 경로 존재 | 승인본 공통 조립, 7월 템플릿, HWPX, 데이터 기반 인포그래픽 |
| 이력 | 기존 run/repository 기반 존재 | 원문→집계→서술→승인→파일 버전 연결 |

기존 Phase 3~5 완료 기록은 해당 범위의 개발 이력이다. “모든 요청 채널에서 월간 데이터를 확보하여 이 PDF 수준으로 납품 가능”하다는 뜻이 아니다. 기존 단순 keyword DOCX writer는 차트를 사용하지 않는 부분이 있어 그대로 최종 템플릿으로 사용할 수 없다.

## 11. 상세 구현 순서와 완료 조건

### M0. 계약과 템플릿 기준 확정

- 기존 schema·repository·workflow와 필요한 정보 목록을 대조한다.
- Narrative 출력/문장 근거/초안·수정·승인 이력/그림 버전의 계약 차이를 설계한다.
- 기존 이름·필드·저장 호환성을 유지하고 신규 계약은 명시적으로 결정한 뒤 구현한다.
- 원본 HWPX 확보 가능 여부와 재사용 자산을 확인한다. 없으면 PDF 기반 대표 페이지 시안을 만든다.
- 완료: 데이터 계약 결정, 고정 스타일과 가변 블록 목록, 미확정 수집 범위가 구분된 문서.

### M1. 실제 수집 범위 확보

- 채널별 권한·한도·과거 검색·원문 확보를 작은 실제 표본으로 검증한다.
- 네이버·다음 뉴스 월간 순회부터 안정화하고 블로그/구글 발견 경로/커뮤니티를 연결한다.
- X·인스타그램·유튜브는 실제 접근 가능한 범위를 확인한 후 어댑터를 구현한다.
- 댓글·재게시·중복·게시일·부분 실패·재시도·재개를 처리한다.
- 완료: 채널별 확보 가능 범위와 제한이 명시되고, 같은 실행 재시도로 중복이 늘지 않음. 미지원은 미지원으로 드러남.

### M2. 분석 데이터와 근거 검증

- 관련성 정제, Fact 검증, 이슈별 매핑, 한국어 TOP20, 대상별 감성 분류를 연결한다.
- 전체/이슈/채널/전월 지표와 산식을 고정하고 근거 문서로 역추적한다.
- 외부 조사는 별도 자료 입력·검수 경로를 둔다.
- 완료: 합계·분모·중복·누락·0분모를 검증한 스냅샷과 이슈별 근거 묶음.

### M3. LLM 초안과 저장

- 제공자 adapter, 장별 프롬프트, 근거 매핑, 숫자·사실 검증을 구현한다.
- 초안 버전, 부분 재생성, 실패 재시도, 비용/호출 중복 방지를 연결한다.
- 순수 템플릿은 fallback 및 테스트용으로 보존한다.
- 완료: 근거 없는 숫자를 넣는 테스트 입력이 차단되고 원문과 연결된 초안이 재조회됨.

### M4. Streamlit 검수·승인

- 수집/분석 점검, 장별 편집, 원문·수치 비교, 버전 비교, 그림 확인을 구현한다.
- 사용자 수정 후 재검증과 승인 버전 고정, 데이터 변경 시 승인 무효화를 연결한다.
- 시각 자료별 편집 설정·원자료·렌더 결과·개별 승인을 저장하고, M5 생성기와 연결하여 생성 후에도 수정·재렌더·재승인할 수 있게 한다.
- 완료: 새로고침·재시작 후 편집·승인이 유지되고 미승인 버전은 최종 export되지 않음.

### M5. 시각 요소와 HWPX 템플릿

- VIS-01~08과 일반 표를 같은 스냅샷에서 생성한다. VIS-05는 외부 조사 있을 때만 사용한다.
- python-hwpx 시제품을 실제 한컴으로 확인한 뒤 12쪽 기준 레이아웃을 구현한다.
- 4개·5개 이슈, 장문, 긴 출처에 맞는 페이지 넘김과 목차를 검증한다.
- 생성된 표·그림·차트·인포그래픽을 M4 UI에 반환한다. 최신 버전이 개별 승인된 자료만 최종 조립하며 문서 배치까지 사용자 검수를 받는다.
- 완료: 수치·출처 일치, 편집 가능한 본문·일반 표, 잘림·겹침 없는 전체 페이지.

### M6. 다중 출력과 월간 운영

- 동일 승인본에서 DOCX·MD 출력, 파일·자산·버전 이력 제공.
- 다음 달 복제·전월 비교·실패 작업 재개·API/CLI 운영 경로를 연결한다.
- 완료: 첫 월간 보고서 전체 흐름을 수행하고 실제 검수·승인·한컴 확인까지 통과.

각 코드 모듈 변경 시 unit test, 단계마다 integration test, 기존 1.0 회귀 검증을 수행한다. 실패한 integration test가 있으면 다음 기능 구현으로 넘어가지 않는다. 문서 작성 자체는 기능 구현 완료를 뜻하지 않는다.

## 13. 다음 작업을 위한 결정 목록

1. 기본 조사어(지역·기관·인물)를 월별 키워드와 함께 수집할지 확정.
2. 댓글 포함 여부와 본문/댓글 지표 분리 방식 확정.
3. 커뮤니티 목록 및 플랫폼별 사용 가능한 접근 권한 확인.
4. 기존 HWPX 원본·로고·표지 사진 확보 가능 여부 확인. 없어도 PDF 기반 시안은 진행 가능.
5. Narrative 출력·승인·시각 자산 버전 계약을 기존 설계와 합쳐 명시적으로 결정.

이 문서는 7월 PDF를 재현할 제품 요구사항과 실행 순서를 기록한 것이다. 실제 월간 수집, 새로운 보고서 생성, python-hwpx 설치, LLM API 연결은 아직 수행하지 않았다.
