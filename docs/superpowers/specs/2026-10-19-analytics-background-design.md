# 통계 집계 백그라운드 실행과 브라우저 메모리 사용 제한

상태: 사용자 승인. 별도 백그라운드 프로세스 실행과 DB에 저장한 결과 중 필요한 값만 정제·조회하는 방식을 요청했다. 기존 JSON 저장 계약을 유지하고 SQLite JSON 조회·SQL pagination을 사용한다.

## 확인한 문제

`streamlit_app/console.py::page_analytics`는 버튼 처리 중 `IssuesToAnalyticsWorkflow.run()`을 동기 실행하고, 완료 후 `st.json(snapshot.metrics)`를 호출한다. 로컬 DB를 읽기 전용으로 확인한 결과 통계 JSON은 약 3.8~8.1MB, 키워드는 최대 46,542개, 키워드 근거 문서 참조는 최대 124,774개였다. 브라우저에서 전체 객체 트리를 렌더링하는 부담을 제거해야 한다. 브라우저 heap 프로파일은 확보하지 않았으므로 정확한 종료 지점까지 재현한 것은 아니다.

## 방식 비교와 제안

- 별도 프로세스(권장): 계산과 형태소 분석기를 UI 프로세스에서 분리한다. 작업 실패를 감지하고 DB 세션도 작업 안에서 생성한다. 스레드보다 실행 관리가 필요하지만 CPU 작업 격리에 적합하다.
- 백그라운드 스레드: 코드가 단순하지만 UI 프로세스의 메모리·인터프리터를 공유한다.

두 방식 모두 전체 JSON 렌더링을 제거해야 브라우저 메모리 문제를 해결할 수 있다.

## 동작

1. 통계 집계 버튼은 별도 프로세스를 시작하고 즉시 반환한다. 로컬 UI 서버 전체에서 집계는 한 번에 하나만 허용하고 중복 클릭·다른 탭의 중복 실행을 막는다.
2. 워커는 URL과 프로젝트 ID만 받아 자체 DB session을 만들고 기존 workflow/repository로 저장한다. ORM session과 Streamlit API를 워커에 전달하지 않는다. schema·DB 테이블·workflow 상태를 신설하지 않는다.
3. 현재 단계, 실제 처리 문서 수/전체 문서 수, 완료·오류를 작은 상태 메시지로 전달한다. 단계는 입력 조회 → 키워드 집계 → 이슈 집계 → 저장이며 성공 표시는 트랜잭션 commit 이후에만 한다. 키워드 처리 건수는 실제 루프의 처리량이고 전체 작업의 예상 완료율로 표시하지 않는다.
4. 사이드바만 `st.fragment(run_every=...)`로 갱신한다. 페이지 이동·브라우저 새로고침 후에도 같은 서버의 작업 상태를 조회한다. 작업 실패 시 재시도를 허용하고, 비정상 프로세스 종료도 실패로 표시한다.
5. 완료 화면은 고유 문서 수·댓글 수·감성/채널 요약·상위 키워드 등 제한된 결과만 표시한다. 키워드별/문서별 근거 ID는 브라우저 위젯에 보내지 않는다. 원자료 JSON은 DB에 그대로 보존한다. 사용자 추가 요청에 따라 UI는 DB에서 필요한 필드·상위 30개 키워드만 조회한다. 이번 UI에는 전체 JSON 다운로드를 추가하지 않아 서버와 브라우저 모두 전체 JSON 로딩을 피한다. 문서 목록은 페이지당 제한된 행만 표시한다.
6. 앱 프로세스 재시작 후 미완료 작업 자동 재개는 이번 범위 밖이다. 작업 리소스를 정리하며 실패한 트랜잭션은 rollback한다. 결과 commit 후 서버가 재시작된 경우 기존 DB 상태에서 완료 결과를 확인할 수 있다.
7. 검색 동작은 변경하지 않는다. UI에 한 줄 전체가 검색 API로 전달되고 전 단어 포함을 별도 강제하지 않는다는 안내만 보완한다.

## 실행·표시 경계

- 서버 공용 작업 manager는 `st.cache_resource`로 유지하고 lock으로 시작/상태 전이를 보호한다. 시작 실패 시 실행 중 상태를 해제한다. 종료한 worker는 join하고 IPC를 정리한다.
- 정상 서버 종료 시 worker를 종료·회수한다. 강제 서버 종료 시 worker는 부모 연결 종료를 감지해 중단한다. 같은 DB의 작업 잠금도 worker 실행 동안 유지해 이전 worker 정리 전 새 서버가 중복 집계하지 못하게 한다. DB 저장은 기존 transaction 경계를 유지한다.
- 진행 상태는 서버 수신자가 브라우저 polling과 독립적으로 소비한다. 최신 상태만 보관하고 중간 메시지를 병합한다. 진행 메시지는 최대 초당 5회이며 성공/실패 최종 메시지는 별도로 보존한다. UI 미접속 상태에서도 worker가 메시지 송신으로 멈추지 않아야 한다.
- TOP 키워드는 30개, 문서 목록은 페이지당 50행, 표시 문자열은 최대 300자로 제한한다. 감성·채널 요약은 라벨과 수치만 선택하며 근거 ID 배열을 포함하지 않는다. 전체 JSON은 일반 렌더링의 session/widget payload에 포함하지 않는다. SQLite JSON 함수로 필요한 scalar와 상위 키워드만 조회한다. 문서의 본문·metadata는 목록 SELECT에서 제외한다.

## 검증

- unit: 서비스의 실제 문서 처리 진행 알림, 빈 입력, 집계 수치 불변.
- unit: 작업 즉시 반환, 중복 방지, 성공/예외/비정상 종료, 실패 후 재시도 및 리소스 정리.
- unit: UI 조회자가 없는 상태에서 대량 진행 알림 후 정상 종료, 시작 실패 시 잠금 해제, worker 종료 후 재실행.
- UI AppTest: 집계 클릭 직후 실행 상태, 사이드바 상태, 완료/오류, 대형 metrics에서 전체 JSON 미출력과 제한된 행 수. UI에 전달된 필드와 행 수·문자열 길이 상한을 직접 검사한다.
- integration: 임시 SQLite에서 프로세스 실행 → snapshot 저장·상태 전이, 실패 시 rollback. 실제 사용자 DB에는 테스트 쓰기를 하지 않는다.
- 기존 `tests_v2`·`tests` 회귀 테스트. integration 실패 시 다음 기능으로 진행하지 않는다.

## 검색어 질문에 대한 코드상 답

입력은 `splitlines()`로 나눠 각 줄을 하나의 query로 저장한다. 네이버·다음은 `query`, 구글·유튜브는 `q`에 그대로 전달한다. 커뮤니티는 사이트 힌트를 추가한다. AIPORG에는 모든 단어를 제목/본문에서 확인하는 AND 필터나 붙여 쓴 한국어 복합어를 확장하는 로직이 없다. 검색엔진의 토큰화·유사어·검색 연산자 의미는 별도이며 모든 단어가 문자 그대로 포함됨을 보장하지 않는다.
